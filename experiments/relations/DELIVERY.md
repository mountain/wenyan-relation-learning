# 交付记录（**不在 patch 范围内**）

本文件记的是**交付本身**，因此刻意不放进 `wenyan-relations.patch`。原因是一个递归：patch 含
`README.md`，若 README 描述交付状态，则每次交付都要改 README、于是又要重生成 patch、
于是交付状态又变——记录追不上被记录的东西。**断开的方式是让交付记录住在被复制物之外。**

## 交付时发生的事，包括出错的部分

上游仓有 husky 预提交钩子（`prettier --write`、`eslint --fix`）。它**改写了七个文件中的三个**：

```
src/inscription/pipeline.ts
src/inscription/reverse.ts
src/inscription/relations.ts
```

改动是**外观性**的——引号风格、数组展开、换行。因此先前草稿里那句
「提交里 7 个文件与本仓逐字节相同」**在推送的那一刻就是假的**。此处记为记录，不抹掉。

**处理方式：已提交的文本成为记录的源头，本仓采纳它。** 三个文件从 `dbe3294` 拷回，
`changes` 完整性台账与 patch 重新冻结，全套测试针对**已交付的文本**重跑（
knowledge / grammar / dialogue / semantics / readiness / conflations 全过；
`changes` 起初因台账哈希变化而失败——那是预期的绊线，重新冻结后通过，哈希链日志字节未变）。

## 工具因此改了检查语义

`tools/relations/rebuild-patch.mjs`：

1. **基线检查由「等于 origin/master」改为「是 origin/master 的祖先」**。交付后 base 是交付提交的
   父提交，而分支头已经走过它；要求相等会让工具在**交付的那一刻**拒绝运行——这正是当时
   实际发生的情况。这条改动是被现象逼出来的，不是预想的。
2. **新增第 5 道检查**：交付提交 `dbe3294` 的七个 blob 与本仓文件逐一比对。于是
   「提交」与「patch」不能再无声地漂开。
