# 语料进入现有 pipeline 之后

Author/self-review: DSH agent session, 2026-09-22. Direction: Mingli Yuan.
语料来源与授权见 `tools/corpus/README.md`；本实验只读语料，不改动语料。

## 问题

把 `data/corpus`（wenyan.corpus.v1，16 部、8208 段、906,907 字）**全量**喂进项目自带的
铭文 pipeline，实际会产出什么？产出的东西在多大程度上能区分不同文本？

这是普查，不是评测。铭文 pipeline 面向的是金文套语（`隹…年…月…干支`、`王在…`、
`令…`、`用乍彝`），诸子/儒家散文是另一个文类。无论分布是什么样——包括「输出根本不区分
输入」——那就是结果，照录进 `evidence.json`。

## 方法

- 通过 Node 类型剥离（`mode: 'strip'`，Node 24/26 唯一可用模式）+ 小型隔离加载器，
  加载**真实发布的四个 TypeScript 模块**，不是副本。
- 全量 8208 段，逐段调用 `runInscriptionPipeline(text, { steps: 3 })`，走 legacy 路径
  （不带 `relationModel`），默认 profile preset。
- 另测：关系语法的覆盖率，以及确认门槛（acknowledgement gate）的行为。
- `contract.json` 先于本次运行写定。

复现：

```sh
node experiments/corpus-pipeline/run.mjs            # 全量，约 0.3 秒
node experiments/corpus-pipeline/run.mjs --sample 500
```

## 实测结果

| 检查 | 结果 |
|---|---|
| 处理段数 / 异常 | 8208 / **0** |
| 置信带分布 | exploratory **8202**、working 6、strong 0 |
| **不同假设句数量** | **2**（全集 8208 段只产出两句） |
| 平均 convergenceScore | 0.0806 |
| 含「三」的段落比例 | 0.16 |
| 关系语法判定 | Unknown **8208/8208**，`KnownFiniteGrammar` 0 |
| 分析器信号 | completion×17、location×11、command×4（合计 32 段有信号） |
| 优化器 | 24,624 步中 accepted 8209（= 8208 次强制首步 + **1 次改进**）、rejected 16415 |
| 确认门槛 | 正确拦截，返回 `blocked: true` |

### 假设句只有两句

`reverseTriCompute` 的假设句来自一个固定集合，**仅由输入是否含「三」选择**：

```
×6895  【新假设（实验性）】贞：其事其成，用乍彝，子孙永宝用。
×1313  【新假设（实验性）】贞：三事其成，用乍彝，子孙永宝用。
```

因此整个语料上，输出对输入的信息量**仅等于「该段是否含三」这一个比特**。

### 分数跟的是「三」，不是文意

| 段落 | convergenceScore |
|---|---|
| 論語 1.1「子曰：學而時習之，不亦說乎？…」 | **0.000** |
| 論語 1.5「子曰：道千乘之國…」 | **0.000** |
| 論語 1.3「子曰：巧言令色，鮮矣仁。」 | 0.021 |
| 論語 1.4「曾子曰：吾日**三**省吾身…」 | **0.493** |

《論語》开篇那句得 0 分，而 1.4 得 0.493，唯一原因就是 1.4 里有「三」。这不是理解，
是这个实验目标本身把「含三」设成了目标特征（`mustContainThree`）。

### 发现并修复的缺陷：标记表简繁不匹配

`scoreOracleTone()`（`src/inscription/reverse.ts`）用一张固定的 8 词标记表给输入打分，
原表中部分标记写的是**简体**，而本语料是繁体，于是它们在繁体文本上**永远不可能命中**：

| 标记（原写法） | 按原写法命中段数 | 繁体写法 | 繁体写法命中段数 |
|---|---:|---|---:|
| `贞` | 0 | `貞` | **154** |
| `万年` | 0 | `萬年` | 10 |
| `永宝用` | 0 | `永寶用` | 0 |
| `王在` / `令` / `成事` / `卜` | 11 / 615 / 17 / 85 | 同形 | — |
| `用乍` | 0 | 同形 | — |

即 8 个标记中有 2 个结构性地无法匹配，`oracleToneScore` 的理论上限被压到 **0.75**。
影响最重的是 `贞`：`貞` 是周易卜辞最核心的用字（全语料 154 段、《周易》一部 171 次），
而这恰恰是 `scoreOracleTone` 想捕捉的信号，被静默漏掉。注意 `永宝用` 是**真的不存在**
（繁体下同样为 0），不是简繁问题——这一点由工具计算而非推断，避免误判。

**已修复**：标记表改为「每项一组变体（简体 + 繁体），任一变体命中即计 1 次」，
分母仍为 8，故现有 profile 权重与阈值保持可比，简体输入行为不变。修复并入
`wenyan-relations.patch`（该文件本就属 patch 范围内的模块）。

修复前后实测（`evidence.prefix-oracle-tone.json` vs `evidence.json`，两者均已存档）：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| `oracleToneScore` 理论上限 | 0.75 | **1.0** |
| `万年` 命中段数 | 0 | **10** |
| `贞` 命中段数 | 0 | **154** |
| 逐部均分提升最大者 | — | **周易 0.1399 → 0.1446**（+0.0047） |
| 平均 convergenceScore | 0.0806 | 0.0809 |
| 置信带分布 | 8202 / 6 / 0 | 8202 / 6 / 0（**未变**） |
| 不同假设句数量 | 2 | 2（**未变**） |

所以：缺陷是真的、也值得修（上限从 0.75 恢复为 1.0，周易这类卜辞文本受益最大），
但它**不是**输出不区分输入的原因——修复后置信带与假设句数量完全没变。

## 结论与下一步

**语料「进得去」：8208 段全部无异常处理，0.3 秒跑完，门槛、信号、增长指标、优化器遥测
都正常工作。** 但「进去之后」产出的东西**几乎不区分输入**——两个固定假设句、99.93% 落在
最低置信带、关系语法零覆盖、优化器在 24,624 步里只找到 1 次改进。

这不说明 pipeline 坏了（它为金文设计，且「三」在实验里是**目标特征**），也不说明语料有问题。
它说明的是两件独立的事：

1. **该语料不能直接当作这个 pipeline 的燃料。** 若目标是让诸子/儒家散文走这条路径，
   reverse 目标 profile 需要一整套**面向该文类**的特征，而不是换 preset 就能解决——
   现有三个 preset 只是同一组权重的不同取值。
2. **要接就得先定「接什么」。** 关系语法在这批文本上覆盖率是 0/8208，因为它的受控句式
   （`「A」授「B」「T」`）是实验自造的，本就不在古汉语里。真正可用的连接点是有序
   验证契约（`learnRelations` 的「先反例后保留」纪律），而不是它的那三个句式。

下一步：

1. ~~修 `scoreOracleTone` 的简繁标记问题~~ **已完成**（见上）。
2. 若确实要做文类适配，先写一份**面向散文的 reverse 目标契约**（哪些特征、为什么、
   如何证伪），再谈实现；不要靠调权重去凑分数。标记表是否要外化为可配置项，
   应在该契约确定后再定。
3. 关系层若要覆盖真实古汉语，需要重新设计受控句式或改走无监督输入，那是一个新实验，
   不是本语料的延伸。

## 边界与不声称

- 不是评测：本 pipeline 在该文类下不存在可用的准确率度量。
- 不对任何段落作文献学或历史学解释。
- `convergenceScore` 是实验目标内部的量，不是质量或正确性度量。
- `oracleToneScore` 命中的是词形巧合（`令`、`卜` 在古汉语中本就常见），不表示 pipeline
  「识别出」了铭文。
- 不评价维基文库的转录质量。
